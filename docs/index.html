What is CANDLE?
CANDLE (CXL-Accelerated Near-Data Logic Evaluation) is an experimental study of database execution on a real computational CXL memory expander, the XCENA MX1P. A device like this is both a memory tier and an execution site. CANDLE asks when running a database fragment on the device beats running it on the host over the same CXL-resident data, once preparation, launch and result handoff are counted.
The question

Should database work move into CXL memory? When does it pay off, how much does it gain, and at what cost once preparation, launch and handoff are counted?

Data residency alone does not decide the plan. A device plan must also launch work, translate addresses through the device's own structures, and deliver a usable result to the next stage. On this CXL 2.0 link there is no hardware back-invalidation, so the software work that makes device updates visible is part of every measurement.

Plans are compared as pipeline fragments, operators finished at a defined result boundary, under a common execution contract that fixes the input, the result and what must be visible at completion.

Scope
PlatformOne device, one stack

One MX1P (PXL SDK 2.0.0, firmware 1.0.4) on one host. Several expanders, CXL switches and memory shared across hosts are not covered; the rules carry over, the crossover points are this platform’s.

PlatformCapped link

CXL 2.0 over PCIe 5.0 ×8 at 32 GT/s, below the device’s supported rate. Bandwidth-bound results would shift with a faster link.

PlatformSoftware coherency

No hardware back-invalidation in this configuration, so the coherency costs describe the software handoff path.

Not measuredArithmetic intensity

The workloads are memory-bound database operators. Compute per byte was not varied, so compute-heavy kernels on the MU cores are not characterized.

Not measuredHost access to CXL memory

Covered in depth by prior work (Melody, SupMario, CXL-Bench). CANDLE uses Host@CXL as its baseline rather than profiling it.

Not measuredWhole queries

CANDLE compares pipeline fragments, operators finished at a defined result boundary, not complete query plans.

Device & SDK
What a computational CXL memory expander is, how the XCENA MX1P is organized, and how software offloads work to it through the PXL runtime. The exact testbed configuration is on the Testbed tab.
About the device

Moving data between host and devices is a growing bottleneck, and memory is one of the most expensive yet least utilized parts of a server. CXL lets a server add memory beyond its DIMM slots. XCENA's computational memory goes one step further: a CXL Type 3 memory expander (CXL.io + CXL.mem) with its own CXL controller and thousands of cores placed next to its DDR5 DRAM. The aim is to move less data and use fewer host CPUs.

Rated vs. as evaluated
XCENA specifies the device as CXL 3.0 with back-invalidation. On our host the link negotiates CXL 2.0 at 32 GT/s, where back-invalidation is unavailable. Making device writes visible to the host is therefore done in software, and CANDLE measures that cost.
Architecture
The host reaches device DRAM with loads and stores over CXL and submits work through PXL.
Development workflow
  1. Write a compute kernel in MU code.
  2. Write a host application using the PXL APIs.
  3. Build both components.
  4. Run on the hardware or the emulator.
Programming model
PXL is the XCENA SDK's runtime library: it manages device resources, loads compute kernels and runs them in parallel on the MUs. A one-shot offload goes through these steps:
memAllocmap device memory load kernelMU binary dispatch handlePXL Map stage inputswrite + flush, or NT + sfence execute()descriptor + doorbell synchronize()completion read resultsinvalidate, then read
Dispatch handle Map
Binds a kernel to a task count and a placement policy. A fresh handle has served no dispatch yet; a reused one accumulates runtime state and gets slower until it is rebuilt.
Tasks and MU threads
A task is the runtime's unit of work, not a thread. By default 16 tasks share one MU thread, so 64 tasks engage four threads. Launch cost depends on how many threads a dispatch engages.
One-shot launch vs. resident worker
A one-shot launch pays the full launch path every time. A resident worker is launched once and polls a queue in device memory; the host publishes descriptors to it and the device dequeues them.
Visibility primitives
pxl::flushHostCache writes back or invalidates host lines; mu::flushCache and mu::flushCacheAll are the device-side calls. Explicit copies use copyToDevice / copyFromDevice (DMA).
What each of these costs is measured on the Tier 1 tab (§4.1, §4.4).

void drain_bench(long* q) {
    if (mu::getTaskIdx() != 0) return;               // one MU thread drains the queue
    long target = ld(q, TARGET), hbatch = ld(q, HBATCH);
    for (;;) { flushCache(&q[T], 8); if (ld(q, T) > 0) break; }  // wait for the host's tail
    long head = 0, sink = 0;
    while (head < target) {
        sink += ld(q, TASKS + head);               // dequeue one descriptor, read fresh
        head++;
        if ((head % hbatch) == 0) { st(q, H, head); st(q, PROC, head); }  // progress, amortized
    }
    st(q, SINKF, sink);                            // checksum: every task was read
    st(q, DONE, 1);                               // st(): store + flushCache
    mu::flushCacheAll();
}

void cxl_resident_worker(std::uint64_t* ctrl, int numTasks) {
    volatile std::uint64_t* c = ctrl;
    std::uint64_t last = 0;
    for (;;) {
        mu::flushCache(ctrl, 64);                // drop the cached ctrl line, re-read memory
        if (c[4]) break;                          // stop flag
        const std::uint64_t seq = c[0];
        if (seq == last) { /* back off */ continue; }
        last = seq;
        if (c[1] == 1) lookup_batch_impl(root, reqs, bytes, true);   // true: flushCache
        else           write_batch_impl(root, reqs, bytes, true);    //   each request line read
        mu::flushCacheAll();                      // results in memory before the done signal
        mu::atomicAdd(reinterpret_cast<std::int32_t*>(ctrl + 8), 1);
    }
    mu::flushCacheAll();
}
