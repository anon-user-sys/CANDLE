What is CANDLE?
CANDLE (CXL-Accelerated Near-Data Logic Evaluation) is an experimental study of database execution on a real computational CXL memory expander, the XCENA MX1P. A device like this is both a memory tier and an execution site. CANDLE asks when running a database fragment on the device beats running it on the host over the same CXL-resident data, once preparation, launch and result handoff are counted.
The question

When does executing a database fragment on a computational CXL expander reduce its elapsed time, including preparation and handoff?

Data residency alone does not decide the plan. A device plan must also launch work, translate addresses through the device's own structures, and deliver a usable result to the next stage. On this CXL 2.0 link there is no hardware back-invalidation, so the software work that makes device updates visible is part of every measurement.

The unit of comparison is a pipeline fragment: operators placed together and finished at a defined result boundary, such as scan and reduce, materialize and return, or partition and probe. Plans are compared under a common execution contract that fixes the input, the result and where it must end up, and what must be visible at completion.

What CANDLE adds
  • Real silicon. Measurements of an implemented computational CXL device and its runtime, complementing simulation and NUMA-emulation studies.
  • Where computation runs, not only where data lives. Passive-expander studies face only data movement; a computational expander adds orchestration, translation and coherency.
  • Contract-complete comparisons. Plans are timed over the same input and result contract, including preparation and handoff, not as isolated kernels.
  • Calibrations tied to decisions. Device-level costs are traced through operators and composite workloads into placement rules for database engines.
  • Open artifact. Harness, kernels, configurations, raw measurements and plotting scripts, with the commands for each figure and table.

About the device

Moving data between host and devices is a growing bottleneck, and memory is one of the most expensive yet least utilized parts of a server. CXL lets a server add memory beyond its DIMM slots. XCENA's computational memory goes one step further: a CXL Type 3 memory expander (CXL.io + CXL.mem) with its own CXL controller and thousands of cores placed next to its DDR5 DRAM. The aim is to move less data and use fewer host CPUs.

The cores are MUs, XCENA's own 64-bit processors based on the RISC-V ISA. MUs are grouped into subsystems (Subs), each divided into clusters that share an L2 cache. All MUs in a Sub run the same kernel binary in parallel.

Rated vs. as evaluated
XCENA specifies the device as CXL 3.0 with back-invalidation. On our host the link negotiates CXL 2.0 at 32 GT/s, where back-invalidation is unavailable. Making device writes visible to the host is therefore done in software, and CANDLE measures that cost.
Architecture
The host reaches device DRAM with loads and stores over CXL and submits work through PXL. A launch prepares a descriptor, rings the device's doorbell and waits for completion; a resident worker is launched once and then serves descriptors from a queue.
Programming model
PXL is the XCENA SDK's runtime library: it manages device resources, loads compute kernels and runs them in parallel on the MUs. A one-shot offload goes through these steps:

Dispatch handle Map
Binds a kernel to a task count and a placement policy. A fresh handle has served no dispatch yet; a reused one accumulates runtime state, so launches get slower (+3.3 µs per dispatch) until the handle is rebuilt.
Tasks and MU threads
A task is the runtime's unit of work, not a thread. By default 16 tasks share one MU thread, so 64 tasks engage four threads and 1,024 tasks engage 64. Launch cost depends on how many threads a dispatch engages.
One-shot launch vs. resident worker
A one-shot launch pays about 1.2 ms each time. A resident worker is launched once and polls a queue in device memory; the host publishes descriptors to it (0.74 µs each, under 10 ns per task in bulk) and the device dequeues them in 22–25 ns.
Visibility primitives
pxl::flushHostCache writes back or invalidates host lines; mu::flushCache and mu::flushCacheAll are the device-side calls. Host non-temporal stores followed by sfence need no flush. Explicit copies use copyToDevice / copyFromDevice (DMA).

Development workflow
With the XCENA SDK, a kernel written for the MU cores is built separately from the host program. The host program loads it and drives it through the PXL runtime.
  1. Write a compute kernel in MU code.
  2. Write a host application using the PXL APIs.
  3. Build both components.
  4. Run on the hardware or the emulator.

Tier 1 · Boundary isolation
Four costs decide whether device execution pays off: orchestration, translation, data movement and coherency. Each is isolated with its own microbenchmark and fitted to a simple model. They are cost categories, not four constants added to every device plan: translation is part of stage execution, and the others arise at control, transfer or visibility boundaries.
Cost accounting
For a plan p with non-overlapping phases, elapsed time under an execution contract C is the sum of preparation, stage execution and the three boundary costs. Translation has no term of its own: it slows the stage's memory accesses, so it is part of stage execution U.
T̂p(C) = Pp + Σs Up,sincludes τ + Σℓ αp,ℓ + Σx βp,x + Σh γp,h

γp,h

Each measured interval is charged once: a transfer measured with its flush is not charged for that flush again. When phases overlap, elapsed time follows the critical path of the plan's event graph instead of a sum (Eq. 2 in the paper).

Timing runs from execute() to the return of synchronize(). Fresh handles show three regimes: flat up to 64 tasks (1,198 µs for one task, 1,277 µs for 64); fan-out from 64 to 1,024 tasks, adding about 700 µs per doubling of engaged MU threads; and linear beyond 4,096 tasks (R² = 0.995). A 3,048-task dispatch costs about 3.5 ms. Most of the time is spent waiting for completion (~570 µs), not on the device.

Reusing a handle is not free: launches grow by about 3.3 µs per dispatch (R² = 0.98), from runtime lifecycle work. Rebuilding the handle every 220 dispatches removes the growth, and the full fresh-handle lifecycle is 1.9–2.2× faster than dispatching through an aged one.

G is the number of distinct 1 GB granules the access stream touches, not the bytes allocated. Latency stays flat through G = 8 and then follows the miss fraction of an eight-entry structure, across region sizes from 16 MB to 2 GB and spans up to 128 GB. A round-robin traversal over more than eight granules costs 689–695 ns against a 99 ns hit baseline, within 1.5% of the fitted penalty.

Only accesses that miss the data cache pay it: at G = 16, 16 target lines cost 62 ns per access, while 4,096 lines cost about 385 ns. The miss cost also grows with the working set, from 362 ns to 635 ns, so the model is a calibration for its measured regime rather than a universal constant.

DMA pays a fixed floor per call; direct host copies avoid it but hit a bandwidth ceiling. Host-to-device non-temporal (NT) stores beat DMA's 10.53 GB/s up to 16 MiB, tie at 64 MiB and fall behind at 256 MiB. Device-to-host direct copies top out at 3.74 GB/s against DMA's 11.88 GB/s, so the return path switches to DMA already at 64–128 KiB.

Instruction choice matters as much as size. NT stores with sfence need no flush, and beat memcpy plus its required flush by 1.9–10.5×. Adding a flush after NT stores anyway costs 67–78% more. Ordinary loads and stores that process data in place are stage execution, not data movement.

Range size, not the dirty fraction, dominates: a 16 MiB flush with 1% dirty lines costs 1.06 ms, almost as much as with every line dirty. Per-object invalidation pays the fixed cost on every handoff; bulk maintenance amortizes it but visits lines no one will read. Which is cheaper depends on how many handoffs there are and what they cover.

At one-shot kernel boundaries the host's actions are enough; omitting them leaves 10–100% stale words. Inside a running kernel there is no completion boundary: mu::flushCache returns before its writebacks finish, so a published counter can overtake its data (0.5% of 12.5 M lines still poisoned). Publishing after mu::flushCacheAll fixes it.
